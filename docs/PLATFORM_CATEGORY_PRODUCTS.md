# H2: category products (owner-reviewed contract)

## Public tool

```json
{"tool":"catalog.category_products","params":{"brand":"sika","url_path":"<exact url_path returned by catalog.brand_categories>"}}
```

The stable category path, not its mutable display label, selects membership.
Brand filtering uses the Magento brand attribute, not product-name text. Parent
paths include descendants with a slash boundary, never similarly named siblings.
The adapter scans the brand's public GraphQL pages before ranking/deduplicating;
it returns an explicit error instead of a misleading partial ranking if the
existing six-page/600-product scan budget is exhausted.

`products` is the **internal window of up to 40**, ordered by distinct sales
invoices descending, then smaller comparable presentation. The inbox owns its
**six visible items** and follow-up question/pagination; this PR does not change
inbox behavior. A 230 kg drum may lead when it has the most invoices, per the
owner's clarified decision. Size ties compare grams/kilograms within mass and
ml/litres within volume. Dimension slots retain deterministic SKU order; mass
is never numerically compared to volume. Unrecognized presentation labels keep
stable SKU order rather than guessing a size.

Products use the closed `catalog.quote_search` price object **minus**
`website_qty` and `in_stock`. `price_with_iva` is integer COP, calculated with
canonical `build_product` / Decimal HALF_UP. No cost, margin or stock is queried,
persisted or returned. Magento supplies membership/name/PDP URL only, never the
canonical public price. `count`, `total_count`, `has_more` describe the bounded
window and full deduplicated category membership.

## Offline snapshot / additive nightly job

The **repo copy only** of `deploy/run_cross_sell_affinity.sh` runs
`business_analyzer.jobs.category_snapshot --category-snapshot PATH --apply`
as a separate process AFTER logging the affinity `ok` line in the nightly
02:30 wrapper. No production cron, service or environment file was changed.
Pair-affinity calculation/store is unchanged; pair counts are never summed as
individual sales. The new snapshot reuses the affinity job's exact-calendar
`_cutoff` and canonical document exclusions. It has a fixed 12-month window,
independent of the pair job's configurable minimum/co-purchase thresholds.

The additional snapshot is a versioned, atomically replaced **local JSON file**,
not a new DB table or migration. This avoids request-time J3 access and requires
no schema rollout. It includes individual invoice counts **and public J3 price /
IVA fields**: keeping prices offline too honors “never J3 live per message”.
Snapshot publication is gated by its own `--apply`; without it, this standalone
CLI computes only. A snapshot compute/publication failure logs a separate
`category_snapshot fail (rc=...)` line, preserves affinity's preceding `ok`
and exit 0, and NEVER enters the affinity retry loop. Failed atomic publication
preserves the old complete file. Affinity retries remain unchanged; snapshot is
attempted once only after affinity succeeds. The pair table and file are not a
distributed transaction; consumers only read their own complete snapshot.

Shared path for both job and BFF:

- `CATALOG_CATEGORY_SNAPSHOT`, if configured;
- otherwise `~/.cache/depotru/catalog-category-products.json`.

The owner must arrange the **same readable path/user** for job and BFF when
choosing to deploy. The temporary file is mode 0600, atomically renamed on the
same filesystem. The BFF only reads it. No production snapshot was generated by
this task. The owner owns deployment, first refresh, cron activation and merge.

Snapshot freshness uses the affinity reader's five-missed-night budget. Missing,
stale, future-dated, corrupt, wrong-window or malformed public-price snapshots
fall back to presentation ordering, with `source` explicitly prefixed
`presentation_fallback:`. Missing SKU coverage uses `incomplete_snapshot` and a
homogeneous presentation-only ranking (not “missing = zero sales”). Available
public prices can still be used; missing prices remain null with the canonical
reason. A missing/unusable entire snapshot means null prices, never live J3 or
Magento-as-price substitution. A usable complete snapshot reports
`source: j3_invoice_snapshot`. Validation rejects extra fields, missing canonical
fields, wrong primitive types, stock and inconsistent price arithmetic.

## Sales-document criterion (explicit allowlist)

Counted codes **only**:

- **FED** — Factura Almacén / principal.
- **FEF** — Factura Florencia / Sika Center.
- **FET** — Factura Calle 5 / distribuciones.

Evidence for that existing sales contract:
`src/business_analyzer/ai/sql_routing.py` (branch invoice selection and
`DocumentosCodigo IN ('FED', 'FEF', 'FET')`). Known return codes
**DVE, DVD, DDD, DDT** from
`src/business_analyzer/core/j3system_devoluciones_conciliacion.py` are outside
this allowlist. **Every other document code, including credit notes, is
excluded by default**, even when its quantity is positive. The canonical
**XY, AS, TS, YX, ISC** exclusions also remain explicit. No guessed list of
credit-note codes is used as a permissive denylist.

The SELECT distincts `(trimmed SKU, DocumentosCodigo, NumeroDocumento)` tuples
before grouping by SKU: repeated lines count once, same invoice number under
different document codes counts separately, and solo-reference invoices count.
No delimiter-concatenation collisions, pair-count multiplication, minimum-20
threshold or 2..40-reference basket filter. Positive quantity and non-null
invoice number are required. Dates run from the affinity calendar cutoff
through the inclusive `as_of` day (exclusive next-day midnight); future invoices
are excluded. Prices are a separate SELECT of `AdmArticulos.ArticulosVenta` and
`AdmLineas.LineasPorcentaje`, with a LEFT JOIN to retain unknown IVA honestly.
Only SELECTs run against J3 when the owner later runs the extended job.
